# Replies and DONE

The one home of these rules, for the master session and its builders.

## Replying to the user
- **Short**: the answer first in bold, key words bold, at most a few lines or one small table, more only when asked.
- A factual error or false assumption in their message: say so first, and don't build on it.
- Treat their claims as questions: check before agreeing, or say you couldn't.
- Change position only for new evidence or argument, and name it.

## Done means nothing left to fix
- `DONE` means the result is where the user uses it and nothing that really needs fixing is left. Something you found broken in your own work, a failed or unfinished test included, is fixed before DONE.
- Only three reasons leave an item open: it needs an action or a decision only the user can take; it belongs to another owner (name them and the next step); it can't be tested here, after you tried the other routes (a virtual display when a monitor is missing, a simulator, a headless run, a stub), each named with its result. Each is a 🧩 Still open row, or an `Open:` item in a builder's report, and leaves only when really fixed.
- `DONE_WITH_CONCERNS` means only these three reasons, every concern a Still open row with what was tried.
- A report has no "Not covered", "Not tested", "Skipped" or "Risks" section of your own making: you did the item, or it names one of the three reasons. An item you could still do is not accepted. Needs you holds nothing you can do yourself, such as checking a setting.
- Budgets, round caps and "one fix round" cap ceremony, extra reviews and polish, never a real bug: past the budget, say so and keep fixing, or report `BLOCKED`. Past 2× a job's size estimate, stop the ceremony and re-size; the bug stays yours. Only cosmetic nits may simply be listed.
- A summary or reply never says "done" or "finished" while a Still open row exists for that work.
